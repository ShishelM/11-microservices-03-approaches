## Задача 1: Обеспечить разработку

Для реализации процессов хранения кода и CI/CD предлагается использовать единую экосистему **GitLab** (облачная версия GitLab.com).

### Соответствие требованиям:

* **облачная система**
  * *Решение:* Используется официальный SaaS-сервис GitLab.com, не требующий развертывания собственной Core-инфраструктуры.
* **система контроля версий Git**
  * *Решение:* GitLab из коробки является полноценной веб-платформой для управления Git-репозиториями.
* **репозиторий на каждый сервис**
  * *Решение:* Архитектура платформы позволяет создавать изолированные репозитории для каждого микросервиса внутри единой логической группы (Group/Subgroup).
* **запуск сборки по событию из системы контроля версий**
  * *Решение:* Механизм триггеров (Webhooks) автоматически запускает конвейер (Pipeline) при событиях `push`, `merge request` или создании тегов.
* **запуск сборки по кнопке с указанием параметров**
  * *Решение:* В веб-интерфейсе GitLab доступна кнопка `Run pipeline`, где перед стартом можно вручную передать любые кастомные переменные (параметры окружения).
* **возможность привязать настройки к каждой сборке**
  * *Решение:* Настройки этапов, переменных и окружений гибко описываются непосредственно внутри конфигурационного файла `.gitlab-ci.yml` для каждого конкретного Job.
* **возможность создания шаблонов для различных конфигураций сборок**
  * *Решение:* Реализуется с помощью ключевых слов `include` (подключение внешних файлов), `extends` (наследование конфигураций) и YAML-якорей (`&` и `*`).
* **возможность безопасного хранения секретных данных (пароли, ключи доступа)**
  * *Решение:* Секреты хранятся в разделе `Settings -> CI/CD -> Variables`. Они шифруются на стороне платформы и могут быть замаскированы (Masked) в логах сборки.
* **несколько конфигураций для сборки из одного репозитория**
  * *Решение:* В одном `.gitlab-ci.yml` можно объявить разные Job для сборки (например, dev, staging, production), разграничивая их через условия `only/except` или `rules`.
* **кастомные шаги при сборке**
  * *Решение:* В блоке `script` каждой задачи можно выполнять любые bash-команды, скрипты автоматизации и вызовы CLI-инструментов.
* **собственные докер-образы для сборки проектов**
  * *Решение:* Для каждой задачи (Job) через директиву `image: name_image:tag` можно указать готовый или собственный Docker-образ, в контейнере которого будет происходить сборка.
* **возможность развернуть агентов сборки на собственных серверах**
  * *Решение:* Программный агент **GitLab Runner** бесплатно устанавливается на любые собственные серверы компании и регистрируется в облачном проекте.
* **возможность параллельного запуска нескольких сборок**
  * *Решение:* Ограничивается только количеством доступных или собственных запущенных GitLab Runners. Платформа распределяет задачи параллельно.
* **возможность параллельного запуска тестов**
  * *Решение:* Реализуется с помощью ключевого слова `parallel` для одной задачи или путем разделения тестов на разные независимые Job в рамках одного этапа (Stage).

#### Обоснование выбора:
GitLab предоставляет монолитный, зрелый и максимально интегрированный инструмент (All-in-One).
Исключается необходимость настраивать сложные интеграции между сторонней кодовой базой, внешним CI/CD-движком (например, Jenkins) и сторонним хранилищем секретов.

## Задача 2: Логи

Для сбора, доставки и анализа логов предлагается использовать стек: **Vector + Apache Kafka + Elasticsearch + Kibana**.

### Соответствие требованиям:

* **сбор логов в центральное хранилище со всех хостов, обслуживающих систему**
  * *Решение:* На каждом хосте разворачивается агент **Vector** в режиме `DaemonSet` или системного сервиса, который агрегирует логи и отправляет их в кластер **Elasticsearch**.
* **минимальные требования к приложениям, сбор логов из stdout**
  * *Решение:* Микросервисы никак не настраиваются на логирование «внутрь себя». Они пишут логи в стандартные потоки `stdout/stderr`, а Vector перехватывает их с уровня контейнеризации (например, из `/var/log/pods` или Docker json-logs).
* **гарантированная доставка логов до центрального хранилища**
  * *Решение:* Между агентами сбора и хранилищем внедряется брокер сообщений **Apache Kafka** (или задействуется встроенный дисковый буфер Vector на хостах — `data_dir`). При сбое Elasticsearch логи будут копиться в буфере без потери данных.
* **обеспечение поиска и фильтрации по записям логов**
  * *Решение:* Индексация текстовых данных силами **Elasticsearch** (или OpenSearch) обеспечивает мгновенный полнотекстовый поиск, регулярные выражения и сложную фильтрацию.
* **обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов**
  * *Решение:* Веб-интерфейс **Kibana** предоставляет доступ к панели `Discover`. Интеграция с корпоративным LDAP/OIDC позволяет гибко разграничить права доступа сотрудников.
* **возможность дать ссылку на сохранённый поиск по записям логов**
  * *Решение:* В Kibana встроена функция `Share -> Short URL`, которая генерирует пермалинк, сохраняющий состояние фильтров, поисковую строку и выбранный таймфрейм для передачи коллегам.

#### Обоснование выбора:
Vector написан на Rust, благодаря чему он значительно производительнее и экономнее по потреблению CPU/RAM, чем аналоги (Logstash или Fluentd). Elasticsearch и Kibana являются стандартом индустрии с мощной экосистемой поиска и удобным UI для разработчиков.

## Задача 3: Мониторинг

Для сбора метрик и визуализации состояния системы предлагается использовать стек: **Prometheus + Node Exporter + cAdvisor + Grafana**.

### Соответствие требованиям:

* **сбор метрик со всех хостов, обслуживающих систему**
  * *Решение:* Центральный сервер **Prometheus** по pull-модели регулярно опрашивает (скрейпит) все целевые хосты, инфраструктурные компоненты и сетевые узлы.
* **сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network**
  * *Решение:* На каждом физическом или виртуальном хосте запускается агент **Node Exporter**, который экспортирует все низкоуровневые метрики операционной системы.
* **сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network**
  * *Решение:* Утилита **cAdvisor** (от Google) запускается на хостах выполнения и собирает детальную статистику по ресурсам, утилизированным каждым конкретным Docker-контейнером (микросервисом).
* **сбор метрик, специфичных для каждого сервиса**
  * *Решение:* Разработчики интегрируют в код микросервисов клиентскую библиотеку Prometheus (`prometheus-client`). Приложение начинает отдавать кастомные бизнес-метрики (кол-во запросов, RPS, ошибки) на эндпоинт `/metrics`.
* **пользовательский интерфейс с возможностью делать запросы и агрегировать информацию**
  * *Решение:* Веб-интерфейс **Grafana** подключается к Prometheus и позволяет выполнять ad-hoc (произвольные) аналитические запросы к базе данных с помощью языка **PromQL**.
* **пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы**
  * *Решение:* В **Grafana** создаются кастомные Дашборды (Dashboards), состоящие из множества панелей: графиков, тепловых карт, круговых диаграмм и текстовых индикаторов со встроенной системой оповещений (Alerting).

#### Обоснование выбора:
Pull-модель сбора Prometheus предотвращает перегрузку микросервисов при сбоях сети. 
Тандем Prometheus и Grafana де-факто признан лучшим бесплатным решением для мониторинга динамических микросервисных сред благодаря гибкости, скорости работы TSDB и развитому сообществу (готовые дашборды под любые нужды).

## Практическая реализация систем логирования и мониторинга (Задачи 4 и 5)

В рамках выполнения дополнительных практических заданий архитектура проекта из предыдущей работы (включая `security-service`, `uploader-service`, `minio` и `gateway`) была успешно объединена и развернута совместно со стеком мониторинга и централизованного сбора логов.

Все конфигурационные файлы добавлены в корень репозитория:
* [docker-compose.yaml](./docker-compose.yaml) — итоговый файл манифеста для развертывания всех 9 контейнеров приложений и инфраструктуры.
* [vector.toml](./vector.toml) — конфигурация агента сбора логов Vector (Задача 4).
* [prometheus.yml](./prometheus.yml) — конфигурация интервалов опроса метрик сервером Prometheus (Задача 5).

### Краткое описание реализации по доп заданиям 4 и 5:

1. **Централизованное логирование (Задача 4):**
   Агент **Vector** настроен на сбор логов из `stdout`/`stderr` контейнеров приложений.  
   В веб-интерфейсе **Kibana** (`http://localhost:5601`, учетные данные `elastic / qwerty123456`) использовать (создать) индекс `vector-*`.

2. **Мониторинг ресурсов (Задача 5):**
   Сбор метрик утилизации ресурсов хоста и контейнеров (CPU, RAM, Network, Disk) осуществляется через **cAdvisor**. Данные агрегируются сервером **Prometheus** и доступны для построения дашбордов и PromQL-запросов в веб-интерфейсе **Grafana** (`http://localhost:3000`, учетные данные `admin / qwerty123456`).

3. **Сквозное тестирование сценариев:**
   Для генерации логов и проверки работоспособности Nginx Gateway (`gateway`) были успешно выполнены три сценария:
   * Анонимное получение JWT-токена через `security-service` (маршрут `/v1/token`).
   * Запрос данных профиля с защищенного эндпоинта `/v1/user` с передачей Bearer-токена.
   * Скачивание файла из хранилища **MinIO** через эндпоинт Nginx с автоматическим срабатыванием внутренней цепочки `auth_request`.
   
   Все этапы прохождения трафика и ответы сервисов были корректно обработаны, структурированы и зафиксированы в Kibana.
